**SOUL files** are structured Markdown documents that define an AI agent's identity, operational rules, quality standards, and decision-making principles. They're the instruction layer between the raw LLM capability (Claude) and the specific, consistent behavior you want from a deployed autonomous agent. A SOUL file is what makes an agent that does research behave like an expert researcher rather than a general-purpose assistant that happens to be searching the web.

Valence AI's five agents — Kaze, Scout, Forge, Ghost, and Sentinel — each have a SOUL file. The SOUL file is why Kaze (the orchestrator) consistently applies the right task routing logic, why Ghost (the writer) consistently matches brand voice across hundreds of missions, and why Sentinel (the monitor) applies the same quality criteria to every deliverable it reviews.

## What a SOUL File Contains

A SOUL file is a structured Markdown document loaded into the agent's context at the start of every session. It defines:

### Identity and Role

Who is this agent? What is its primary function? What does it not do?

```markdown
# Ghost — Content Specialist

You are Ghost, Valence AI's writing agent. Your role is to take
structured research, data, and briefs and transform them into
polished written deliverables: emails, reports, blog posts,
campaign copy, and documentation.

You are NOT a researcher. You do NOT conduct web searches.
You do NOT execute code. You do NOT review other agents' work.
You write. That is your function.
```

Clear role definition prevents generalist drift — the tendency of a capable LLM to attempt tasks outside its defined scope "helpfully," often with worse results than a specialist would produce.

### Quality Standards

What does "good output" look like for this agent's specific function?

```markdown
## Quality Standards

Every written deliverable must:
- Match the specified tone and format from the mission brief
- Be factually accurate to the research provided — never invent details
- Meet length requirements (±10% of specified word count)
- Include all required sections from the brief
- Reference specific, accurate details from Scout's research
  (not generic placeholders)
- Be ready for human review without requiring significant rework

Failure modes to avoid:
- Generic templates with company name swapped in
- Invented statistics or unverified claims
- Mismatched tone (formal email sent as casual, or vice versa)
- Missing required sections from the brief
```

Quality standards in SOUL files are the specification for Sentinel's (the monitor agent's) review. Sentinel reviews Ghost's output against Ghost's stated quality standards — creating a closed loop where the agent's definition of quality matches the reviewer's criteria.

### Decision Rules

When faced with specific situations, what should the agent do?

```markdown
## Decision Rules

**If research input is incomplete:**
- Do not fabricate missing details
- Draft what you can from available information
- Flag missing information explicitly in your deliverable
- Return to Kaze with a specific list of what's needed

**If the brief is ambiguous:**
- Apply the most reasonable interpretation
- Note your interpretation at the top of the deliverable
- Complete the task based on that interpretation
- Do not stall waiting for clarification on minor points

**If your output fails Sentinel review:**
- Read all feedback carefully before revising
- Make only the changes Sentinel specified
- Do not rewrite sections that weren't flagged
- Resubmit the revised version, not a new draft
```

Decision rules eliminate the ambiguity that causes agents to behave inconsistently on edge cases. Without explicit rules, two identical situations might produce different agent responses depending on subtleties in the LLM's sampling. Decision rules make behavior deterministic where it needs to be.

### Tool Usage Guidelines

Which tools does this agent use, and when?

```markdown
## Tools Available

**post_deliverable:** Use when your written output is complete and
ready for Sentinel review. Include the full text — never just a summary.

**update_task_status:** Use to mark your task as in_progress when
you begin writing, and then use post_deliverable (not this) when done.

**read_task:** Use to access the mission brief, research inputs,
and any specific instructions for this deliverable.

**flag_for_human_review:** Use ONLY when:
- The brief contains a direct ethical concern
- You've failed Sentinel review 3+ times and believe the criteria
  are contradictory
- The task requires information you cannot obtain from provided research
```

Tool guidelines prevent agents from using tools incorrectly or using the wrong tool for a situation. An agent that posts incomplete deliverables, or calls `flag_for_human_review` on every minor uncertainty, creates operational noise. Explicit tool guidelines calibrate when each tool is appropriate.

### Operational Rules

Hard constraints that override any other instruction.

```markdown
## Hard Rules (Never Violate)

1. Never invent information that wasn't in your research inputs
2. Never post a deliverable that is obviously incomplete
3. Never modify another agent's outputs — only your own
4. Never skip Sentinel review by marking tasks complete directly
5. Stop at turn 15 maximum — post partial results and hand off cleanly
   rather than running the session to context limit
```

Hard rules are the safety layer. They define behaviors the agent must never exhibit regardless of what the task brief says or what seems helpful in the moment.

## How SOUL Files Are Used

### Loading at Session Start

When OpenClaw starts an agent session, the SOUL file is loaded and injected into the agent's context before any task-specific information arrives. The SOUL establishes the agent's operating framework; the task provides the specific work to do.

This sequence matters: the SOUL file's instructions take precedence because they're foundational to how the agent operates. Task briefs customize what the agent does within the identity and constraints the SOUL establishes.

### Version Control and Deployment

SOUL files are Markdown files in the project repository — version-controlled like code. Updates to agent behavior go through the same review process as code changes:

1. Edit the SOUL file locally
2. Review the changes (what behavior is this changing?)
3. Deploy to the server
4. Monitor agent behavior on the next few missions

This makes agent behavior auditable and rollback-able. If a SOUL file update causes quality problems, reverting to the previous version is a `git revert` and a deploy — not debugging a complex neural network.

### Customization for Enterprise Customers

Valence AI allows enterprise customers to customize SOUL files to match their specific context:

- **Brand voice:** Add company-specific writing style guidelines to Ghost's SOUL
- **Quality criteria:** Add industry-specific quality standards to Sentinel's SOUL
- **Domain knowledge:** Add company-specific context (product details, ICP, competitive positioning) to all agents' SOULs
- **Workflow preferences:** Add specific output format requirements, preferred tools, or escalation thresholds

Customers modify SOUL files without writing Python — the agent behavior configuration is Markdown, readable by anyone on the team.

## SOUL Files vs. System Prompts

SOUL files look like system prompts, and they serve a similar function. The distinction is organizational and operational:

**System prompts** are typically embedded in application code — strings in a configuration object or database field. They're versioned with the application, not independently, and require developer access to modify.

**SOUL files** are standalone documents in a file system — independently versioned, deployable independently from the application, and readable without understanding the codebase. A customer can read their agents' SOUL files and understand exactly how those agents are configured to behave.

For enterprise AI deployments where auditability and customer customization matter, the SOUL file model is more appropriate than system prompts embedded in code.

## SOUL Files and Agent Quality

The quality of an AI agent deployment is directly correlated with the quality of its SOUL files. Vague SOULs produce inconsistent agents. Specific SOULs with well-defined quality criteria, decision rules, and hard constraints produce agents that behave predictably across thousands of varied tasks.

The evolution of Valence AI's agent quality over time is largely the evolution of SOUL files — adding more specific decision rules, refining quality criteria based on Sentinel's review patterns, adding hard rules that address edge cases discovered in production, and incorporating customer-specific context.

This is agent improvement without model retraining: the agent's underlying capability (Claude) stays constant; the SOUL file that directs that capability becomes more precise.

## Frequently Asked Questions

### Can customers see and edit their agents' SOUL files?

Yes, for enterprise customers. Valence AI provides SOUL file access as part of enterprise customization. Business customers can review their agents' SOUL files and request modifications without requiring Python knowledge. Changes go through a review process before deployment.

### Do SOUL files need to be updated when Claude's underlying model is updated?

Sometimes. When Claude's capabilities significantly change, SOUL files may need updates — for example, if Claude's default behavior on a specific task type changes. In practice, SOUL files are stable across model updates within the same model family. Major model version upgrades (e.g., moving from Claude Sonnet 4.6 to a hypothetical future version) may warrant SOUL file review.

### What happens if an agent receives instructions that conflict with its SOUL file?

SOUL file instructions take precedence. If a task brief instructs an agent to do something its SOUL file prohibits (fabricate data, skip quality review, use a tool outside its designated scope), the SOUL file's hard rules override the task instruction. The agent flags the conflict rather than violating its constraints.

### How long are SOUL files?

Valence AI's production SOUL files range from 400-1,200 lines depending on the agent's complexity. Kaze's SOUL (the orchestrator) is longest — it has the most complex decision logic for task routing, delegation, and mission management. Specialist agents (Ghost, Scout) have shorter SOULs focused on their narrower scope.
